## 1. What this is and why

Navigation layers are created **per map**, at load, by `CreateNavigationLayers` (`NAVLAYERS`):
**Land, Amphibious, Hover, Air always; Submarine and Sea only if `Engine.HasWater()` is true.** A
`NavmapModifierTemplate` is a **world-space, axis-aligned rectangle** (`float2 size`, centered on
wherever its owning prefab instance is placed, **no rotation support**) that blocks pathing on
**one named layer**.

**The set of layers a prefab can ever block is fixed at prefab-template creation time.** A prefab
that needs to block N layers carries N modifier child entities — one per layer — built via
`NAVLOADER.AddNavmapModifierTemplates(parentEntityName, layerNames, size, disabled,
hierarchyEntities, navmapModifierTemplates)` when the prefab **template** is constructed. You
cannot add or remove which layers a specific *instance* blocks; you can only resize or
enable/disable the layer-modifier children already baked into the template it was instantiated
from.

This matters for map authoring because a purely decorative prop (a floating spire footprint, a
cliff mesh with no native collision) has no pathing consequence by default — nothing stops a unit
walking, flying, or sailing straight through it — unless the map author explicitly attaches a
navmap-modifier-carrying prefab at that location. This spec formalizes how to do that from
`<MapName>_data.lua`, with zero engine or `mapUtils.lua` changes, for both the all-layer case
(§3, confirmed shipped) and the single/partial-layer case (§4, confirmed shipped).

### 1.1 The six navigation layers and their height bands (ratified 2026-08-30, `ARCH_22_12_MaskGenerationAlgorithmAndScope.md`)

| Layer | Always created? | Height band | Max slope |
|---|---|---|---|

| `Amphibious` | yes | -∞ to +∞ | 30° |

| `Air` | yes | -∞ to +∞ | ∞ (unrestricted) |

## 3. Technique A — reusing the global all-layer barrier prefab (ratified, confirmed shipped)

**Use when:** a location must block **every** mobility type together (air + land + sea + amphib +
hover + sub) — e.g. a decorative prop's footprint that should be fully solid.

**Confirmed working live in-game, twice, this session (human confirmation: "It worked").** Zero
`engine`/`mapUtils.lua` changes needed.

**The sequence**, run per desired blocker location, from `<MapName>_data.lua`:

1. `Engine.InstantiatePrefab(_G.PlayableAreaBarrierPrefabID, position, scale, rotation)` — spawn a
   fresh instance of the engine's own singleton barrier prefab at the desired world position.
2. `NavmapModifiers.GetNavmapModifierIDs(instanceId, _G.PlayableAreaBarrierLayers)` — resolve the
   per-layer modifier-child IDs already baked into this instance (all layers, since this prefab's
   template was built from `GetAllNavigationLayerNames()`).
3. `SetNavmapModifiersSize(...)` on those IDs — the world-space AABB the blocker actually occupies.
4. `SetNavmapModifiersEnabled(true, ...)` on those IDs.

This is **exactly the same sequence** `BARRIER`'s own `CreateBarrier`/`SetBarrierSize`/
`SetBarrierEnabled` already use for the map-edge walls — the technique is "call the engine's own
established barrier-authoring pattern against a location of your choosing," not a new mechanism.
Exact function signatures/argument order are ground truth in `NAVMOD`/`BARRIER`; this spec states
the sequence and division of responsibility, not a byte-for-byte call transcription.

**Host/client split — navmap modifiers are host-only, mirroring `BARRIER` exactly:**

- **Host** sets the real `NavmapModifiers` (steps 2-4 above). This is simulation-authoritative —
  the actual pathing block every mobility type respects.
- **Client** sets **only** the local building-placement grid modifier
  (`Engine.SetLocalGridModifierSize`/`Enabled`) — a client-local visual/placement-preview aid, not
  a pathing authority. It does **not** call `NavmapModifiers.*` at all.

This split is not a simplification invented for this technique; it is the same
host-authoritative/client-cosmetic division `BARRIER`'s own `SetBarrierSize`/`SetBarrierEnabled`
already carry for the exact same primitive.

**Every step above that can throw MUST be independently `pcall`'d** — see §6.1 for why this is not
optional polish and a real, load-bearing regression that "correct ordering" alone did not fix.

## 4. Technique B — a purpose-built partial-layer prefab (confirmed shipped)

**Use when:** a location must block only a **subset** of layers (e.g. Sea-only — confirmed working
live in-game on Pandemonium Isthmus, human confirmation: "sea blocker working"). This is now a
shipped, verified pattern, the same evidentiary bar as §3. One nuance preserved from the original
design pass: the specific stray-1×1-blocker failure mode described just below (what Technique A
would do if misused for a partial-layer case) was never itself deliberately reproduced and observed
failing — only the working Technique B alternative was built and confirmed; treat that specific
failure-mode description as reasoned from source (`BARRIERLOADER`), not reproduced.

**Why Technique A cannot be reused for a partial-layer blocker.** `_G.PlayableAreaBarrierPrefabID`
has **all six** layers baked into its template at `BARRIERLOADER`'s creation time. Requesting or
enabling only, say, the `Sea` modifier bone on an instance of that prefab leaves the **other five**
layers' modifier children on that **same instance** sitting at their template-creation defaults:
**`disabled = false`** (i.e. active, not a harmless placeholder) and **`size =
EngineClasses.float2(1,1)`** — the placeholder size `BARRIERLOADER`'s `CreatePlayableAreaBarrierPrefab`
bakes in for every layer. The consequence is not cosmetic: **every such instance silently drops a
real, active 1×1-world-unit blocker on Land/Air/Hover/Amphibious/Submarine at its position**,
regardless of which single layer the author intended to touch.

**The correct pattern:** a **new, purpose-built prefab**, constructed the same way
`CreatePlayableAreaBarrierPrefab` is constructed, but passing only the desired `layerNames` subset
to `NAVLOADER.AddNavmapModifierTemplates` instead of `LAYERS.GetAllNavigationLayerNames()`. Because
the layer set is fixed per prefab template (§1), a Sea-only blocker needs its own template that was
**never given** the other five layers' modifier children in the first place — there is no
enable/disable path that can remove a layer a template was built with, and no size big enough to
make a stray 1×1 blocker harmless in general (it is still a real obstruction wherever it lands).

**Where this new prefab lives today: a small map-local helper function directly in that map's own
`_data.lua`.** This matches the "zero engine changes" philosophy Technique A already established —
a hand-authored per-map helper, not an engine-file change, following the exact same
`AddNavmapModifierTemplates`/`InstantiatePrefab`/`GetNavmapModifierIDs`/`SetNavmapModifiersSize`/
`SetNavmapModifiersEnabled` shape as §3, minus the "reuse an existing global prefab ID" shortcut —
this variant must build (and cache, per Lua state) its own prefab ID once, then instantiate it per
location exactly as §3 does.

**Promotion to a shared engine helper — recommended, not mandated, and still genuinely open.** A
map-local prototype is the currently-proven, lowest-blast-radius approach and matches this project's
established don't-touch-`engine`/`mapUtils.lua`-for-per-map-behavior philosophy
(`MAP_SCENARIO_SPEC.md` throughout; `ARCH_15_04`'s "zero `mapUtils.lua` changes" precedent for the
Scenario system). It should **stay** map-local until it is proven twice — the same evidentiary bar
this very spec's own existence was held to (Technique A was formalized only after being confirmed
live twice, not after its first success). Technique B itself has so far been confirmed live once
(Pandemonium Isthmus, Sea-only); the "proven twice" bar for *promoting the helper to a shared file*
has not yet been met and remains an open item. Concretely: build it once, per-map, in `_data.lua`;
the first time a **second** map needs the same partial-layer-subset pattern, promote the
construction helper (not the per-map layer-list choice, which stays map-authored data) to a shared
`common/loading/*.lua` helper, mirroring `navmapModifierLoader.lua`'s own existing shape. Do not
promote pre-emptively on the strength of a single map's need — that inverts the same
proven-before-generalized discipline this pack applies elsewhere (e.g. `ARCH_19_02`'s
genericity split, `ARCH_15_10`'s "ported verbatim only once shown to be universal" reasoning).

## 5. ⚠️ The per-Lua-state execution nuance — read before debugging this twice more

**This is a different phenomenon from `MAP_UNIT_SPAWNING_SPEC.md` §2's double-execution hazard —
do not conflate them.** That section documents `<map>_data.lua` executing **twice within one host
Lua state** because two host-side callers (`LoadMapData` and the debug loader) spell the same
`Import()` path differently, causing a cache miss. This section documents a **separate, orthogonal**
fact about a **different axis: Lua state count**, not `Import` cache keys.

**Confirmed by reading `SCRIPT` directly:** `init()`'s `if isClient then IsClient = true else
IsHost = true end` makes `IsHost`/`IsClient` mutually exclusive **within one Lua state** — a single
state is never both. But a solo/listen-server match runs **two separate Lua states**, and
`InitLobby` calls `LoadMapData` **once under each state's own `if IsHost` / `else` branch**. Since
`LoadMapData` is what `Import`s and runs `<map>_data.lua`'s top-level body (`MAP_UNIT_SPAWNING_SPEC`
§1 step 1), **the whole per-map chunk — including any blocker-spawning function called from its
shared `NewThread` — executes once per state**, and **each state's own single call correctly takes
the branch appropriate to its own role.**

**The practical consequence:** if you observe a blocker-spawning function apparently "running
twice" in a solo/listen-server test, the correct diagnosis is very likely "one call in the host
state, one call in the client state, each legitimately taking its own `IsHost`/`IsClient` branch" —
**not** a bug, and **not** the same `Import`-cache-key hazard `MAP_UNIT_SPAWNING_SPEC` §2 describes.
Confirmed misdebugged this exact way, live, twice, by two different Claude sessions, before being
correctly re-derived. Both hazards are real and can co-occur (a host-side chunk re-execution from
§2's cache-miss AND a separate client-state execution from this nuance are not mutually exclusive);
treat them as two independent counting axes, not one.

## 6. Ordering law inside the shared `NewThread` — extends the existing law, does not replace it

Navmap-modifier blocker work runs inside the **same single `NewThread`** `MAP_UNIT_SPAWNING_SPEC`
§4 and `MAP_SCENARIO_SPEC` §3.1 already govern — it does not get its own thread (only one
`NewThread` per script is honored; see `MAP_UNIT_SPAWNING_SPEC` §4). Two ordering constraints,
each paid for by a real regression this session, on top of that existing law:

1. **Must run AFTER both host-side `SetPlayableArea` calls are done** (the throwaway `{-1000,-1000,1,1}`
   nudge and the real area) — never before. Prefabs instantiated while the playable area is still
   the tiny throwaway rectangle are a plausible culling target. **This constraint is about
   correctness, not error propagation — `pcall` (§6.1) does not substitute for it.**
2. **Must run LAST, after scenario unit spawning — not early.** Blocker work once sat AHEAD of the
   unit spawn; when it threw (§6.1's missing-`Import` story), the throw silently cancelled
   everything after it in the same `NewThread` callback, killing every scenario unit as collateral
   damage. Placing the blocker calls last, after everything load-bearing, means a blocker throw can
   no longer cascade into anything else — a second, independent layer of protection on top of every
   call also being individually `pcall`'d (§6.1).

**The concrete order that satisfies both constraints on Pandemonium Isthmus today** — verified by a
direct read of the live `<MapName>_data.lua` this pass, not assumed or relayed secondhand:

```
(a) host-only SetPlayableArea ×2 (nudge, then real)
(b) host-only scenario unit spawning, pcall'd
(c) SpawnAirBlockerNavmapModifiers, pcall'd — LAST on purpose; the live file's own comment reads
    "Nothing load-bearing goes after it, and its errors can no longer cascade into anything else"
(d) SpawnSeaBlockerNavmapModifiers, pcall'd in its own separate pcall from (c) — one blocker's
    failure must never take another one down
```

Steps (c)/(d) run in **BOTH** Lua states (§5); each takes its own `IsHost`/`IsClient` branch
internally.

**This matches, rather than differs from, `MAP_SCENARIO_SPEC` §3.1's own documented live order**
(area → units → prefab/navmesh work last) and `MAP_UNIT_SPAWNING_SPEC` §4's illustrative code
sample. **An earlier version of this section claimed a discrepancy here — that claim was wrong,**
based on an intermediate mid-fix state relayed secondhand rather than the live file's actual final
shape, and is retracted. Both of those specs' own text on this point can be trusted as still-current.

### 6.1 ⚠️ Ordering reduces the CHANCE of a failure; `pcall` removes the CONSEQUENCE — both are required, and neither substitutes for the other

**This is the single most important lesson from this session's debugging, and it is easy to get
only half right.** On Pandemonium Isthmus, the all-layer air blocker went through **multiple**
rounds of live debugging that each fixed a real `NewThread`-ordering problem (blocker before/after
`SetPlayableArea`; blocker before/after the unit spawn) **without ever fixing the actual
failure.** Every one of those ordering fixes was individually correct and individually
insufficient — the blocker still did not appear.

**The real root cause, found only afterward:** a scripted rewrite of the rectangle table (a
find-and-replace regenerating a `*_BLOCKER_RECTS` table) silently **deleted an adjacent line** —
`local NavmapModifiers = Import("common/navmapModifiers.lua")` — that happened to sit inside the
overwritten span. Without that line, `NavmapModifiers` resolved to a **nil global**, and every
host-side call to `NavmapModifiers.GetNavmapModifierIDs(...)` **threw**. That throw was invisible
for the exact same reason every other throw in this thread is invisible: swallowed by
`threads.lua`'s `ResumeThread`, with `Warn()`/`Log()` routed to a non-functional F1 console. No
amount of ordering the blocker call relative to `SetPlayableArea` or the unit spawn could have
fixed this — the bug was not an ordering bug at all.

**Binding rules, on top of §6's ordering constraints, not instead of them:**

1. **Every blocker-spawning call must be wrapped in its own `pcall` inside the shared `NewThread`
   — not merely placed in a safe position.** Ordering only reduces the *chance* something upstream
   fails first and cancels the callback before the blocker call runs. `pcall` removes the
   *consequence* if the blocker call itself throws, for **any** reason — including a bug that has
   nothing to do with ordering, like the missing-`Import` case above. **Once every risky call in
   the thread is individually `pcall`-wrapped, the exact relative ordering between them stops being
   fragile.** The one ordering constraint that remains genuinely load-bearing even under full
   `pcall` coverage is §6 point 1 (`SetPlayableArea` must be final before blocker prefabs
   instantiate) — that one is about which world-state the prefab sees, not about error propagation,
   so `pcall` does not and cannot fix it.
2. **Named failure mode to watch for:** forgetting `local NavmapModifiers =
   Import("common/navmapModifiers.lua")` (or any similar per-file `Import()` alias) produces **no
   error at the missing line** — Lua does not complain about an unused-but-expected local. The
   only symptom is a throw **one call later, inside `NewThread`**, invisibly. Anyone regenerating a
   Lua data table **via a script** rather than a manual edit — rectangle lists, scenario tables,
   anything — should **diff the whole function the table lives in, not just the table itself.** A
   wide find-and-replace can silently delete adjacent real code (an `Import` alias, a helper
   function, anything sharing the overwritten span) with no diagnostic of any kind.
3. **"The ordering checks out" is not sufficient evidence that a fix is correct.** Each of the
   ordering-only fixes attempted on this bug was independently justified by §6's real constraints
   and independently failed to fix the actual symptom. Treat a clean re-derivation of ordering as
   necessary, not sufficient, confirmation — if the blocker still does not appear after an ordering
   fix, look for a thrown exception upstream of (or inside) the blocker call itself before
   re-ordering again. Wrapping the call in its own `pcall` and having it log a countable signal
   (`MAP_UNIT_SPAWNING_SPEC` §7 — units are the only reliable diagnostic in this build) turns an
   invisible throw into a visible one and would have shortened this exact regression considerably.

## 7. Mask-to-rectangle authoring workflow (current manual process, outside SanGen)

**This is how the rectangle lists for both live tests were actually produced — entirely outside
SanGen today, an ad hoc Python pipeline run by hand.** Recorded here as the current process; §7.1
flags it as a strong candidate for a future SanGen-native feature.

1. Author a mask texture (grayscale or RGB — both used successfully) in the map's own `Textures/`
   folder, at the **same resolution as `heightmapResolution`** (2049×2049 confirmed on Pandemonium
   Isthmus). White = area to block.
2. Threshold at roughly 50% of the mask's value range; connected-component-label the result
   (8-connectivity); drop components below ~20px as antialiasing noise.
3. Per component, decompose to rectangles in two passes:
   a. An **exact (zero-overshoot) greedy largest-rectangle-in-binary-matrix decomposition** first —
      guarantees 100% coverage of every white pixel by construction.
   b. A **greedy agglomerative merge pass** — repeatedly replace the two rectangles whose union
      bounding box adds the fewest net-new black pixels (measured via a 2D integral/summed-area
      image over that component's true mask, so overlap between already-merged rectangles is never
      miscounted) with that single bounding box, stopping once the cheapest remaining merge would
      add more black pixels than a chosen threshold.
4. **The merge threshold is the human-tunable knob** trading rectangle count against black-area
   overshoot. A genuine same-mask, same-32-component sweep on this map's air-blocker mask confirms
   the tradeoff directly: 256px → 206 rects, 29.3% overshoot; 512px → 139 rects, 41.5% overshoot;
   1024px → 88 rects, 58.8% overshoot. A **separate, earlier** pass at a lower threshold (16px) on a
   slightly different edit of the mask (also 32 components, near-identical sizes — e.g. the spire
   pair measured 4308px there vs. 4369px in the sweep above) produced 815 rects at **3.5%-15.3%
   overshoot per individual component (no aggregate computed for this pass)** — a qualitative
   reference point for the accuracy end of the knob, not a fourth row in the same sweep as the three
   numbers above.
5. **Always verify by rasterizing the union of all kept rectangles and diffing against the true
   mask** — missed-white-pixel count must be exactly zero; overshoot is measured as a per-component
   percentage, never estimated from a sum of rectangle areas (merged rectangles can overlap each
   other; that estimate can be 100×+ wrong).
6. **No rotation is possible** — `NavmapModifierTemplate.size` is a plain axis-aligned `float2`
   (§1) — so a diagonal or rotated real-world feature gets staircase-approximated by axis-aligned
   boxes. This is inherent to the engine primitive, not a limitation of the pipeline above.

## 8. Pixel↔world coordinate convention for mask-derived rectangles — distinct from the entity-position convention

Empirically validated **twice** this session: once against 164 real prop instances already present
in the `.sanmap` (96% agreement), once by human confirmation in-game that the resulting blocked
area sat in the correct place.

```
x = (heightmapResolution - 1) - col
z = row
```

**This is the SAME convention `SANMAP_FORMAT_SPEC.md` already documents for `heightmap.raw`
sampling** (`row = z; col = (N-1) - x`), used here in the **inverse direction** (pixel → world,
rather than world → pixel) — because a hand-authored `Textures/` mask is the same raster-asset
family as `heightmap.raw`, not a `.sanmap` JSON entity-position field.

**Do not conflate this with the different, separately-documented `.sanmap` entity-position
convention** (`SANMAP_FORMAT_SPEC.md`: `world.z = length - z - 1`, an axis the spec itself states
cannot be fully resolved from shipped maps alone — see that spec's own "Open question" note). These
are **two different conventions for two different kinds of coordinates** — one for raster-texture
pixel indices, one for JSON entity position fields — and a reader must not assume one informs or
corrects the other. `SANMAP_FORMAT_SPEC.md` carries a short pointer to this section immediately
after its own heightmap-sampling convention, for exactly this reason. §9.2 below states the SAME
convention applies, unmodified, to the SanGen-native rasterization stage's own world→pixel direction.

## 9. Ownership and scope

Per the layer-classification precedent `ARCH_15_01_LayerClassification.md` established for the Map
Scenario system: the **hand-authored Lua half** of this technique (§1-§8 above) is **game-side Lua,
not SanGen C++**. It runs inside the engine's own script sandbox, at map-load time, on the player's
machine — it does not occupy a slot in the Constitution §1 layer stack, for the same reason the
Scenario system does not. Full ruling: `ARCH_22_09_OwnershipScopeRuling.md` §22.9, unmodified by
this update.

### 9.1 The SanGen-native successor — ratified into the owned architecture (2026-08-30)

**Unlike §1-§8, the mesh-ingestion/mask-generation successor DOES occupy real slots in the
Constitution §1 layer stack** — `SYS` (a `.sanmodel` binary reader), `IO` (visual-LOD extraction,
pack-asset resolution, a run-scoped mesh cache), `MATH` (rigid-transform + triangle/plane
primitives), `PROC` (plane-slice/rasterize/decompose kernels, CPU-only dispatch), `PARAMS` (the
resolved rectangle-list type and per-layer merge settings), a new one-shot human-triggered
`PIPELINE` bake responsibility (never wired into the automatic regeneration DAG), and `UI` (a
Navmesh Tab). Full ruling, ratifying four 2026-08-30 domain-expert design consults:
`ARCH_22_NavmapModifierBlockers.md` §22.10-§22.17.

**v1 scope: Sea + Submarine only**, per §1.1's height-band table — the two layers whose bands are
genuinely water-relative. Land/Amphibious/Hover/Air are explicitly deferred to a future, structurally
different "full mesh silhouette" technique, not designed by this update
(`ARCH_22_12_MaskGenerationAlgorithmAndScope.md`).

**Determinism:** the resolved rectangle list is baked once, human-triggered, into an ordinary
`Params::` field — never read live by the automatic regeneration pipeline, never independently
recomputed by more than one machine. It sits outside `DETERMINISM_SPEC.md`'s bit-exact cross-machine
regeneration bar by construction, achieving cross-machine parity by transport (as ordinary recipe
data) rather than by recomputation — full reasoning: `ARCH_22_13_BakedArtifactStorageAndDeterminism.md`.

### 9.2 The successor's own coordinate convention

Unmodified from §8 above — the SanGen-native rasterization stage's world→pixel direction is the
exact inverse of §8's pixel→world formula, over the same `heightmapResolution` raster space,
distinct from the separate `.sanmap` entity-position convention exactly as §8 already states.
