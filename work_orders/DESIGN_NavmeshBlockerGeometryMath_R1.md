# DESIGN_NavmeshBlockerGeometryMath_R1 — MATH placement & performance advisory

**Scope:** advisory only — reusable MATH primitives and CPU/GPU dispatch guidance for the plane-vs-mesh navmesh-blocker feature two other experts are designing (`.sanmodel` ingestion; plane-intersection/rasterization/rectangle-decomposition PROC). No PARAMS shape, no PROC stage, no algorithm design — that stays with the Generator Expert per `ARCH_22_09_OwnershipScopeRuling.md` §22.9's explicit "not designed here" note.

## 1. Survey of `src/math/` (every header read in full)

**a. Rigid-transform of a plane/point — `src/math/RigidTransformPivot_MATH.h` (43 lines, confirmed by direct read).** Today it holds exactly three functions: `RotatePointAroundPivot` (2D X/Z pivot rotation, used by the Bundle/Assembly move-rotate tool per its own header comment), `MultiplyQuaternions` (Hamilton product, scalar out-params), and `YawQuaternion` (yaw-only quaternion construction). **It does not contain a 3D quaternion-vector rotation, a full rigid point-transform (position+rotation+scale), an inverse transform, or anything plane-related.** `Placement_Transform_PROC.h` (read directly — the only other place a rigid instance transform is built) confirms the instance-transform shape SanGen already uses: position + quaternion `(x,y,z,w)` + per-axis scale `(scaleX,scaleY,scaleZ)`, quaternion built the same Hamilton-product way. So `RigidTransformPivot_MATH.h` is the right *home* (same "rigid-transform primitives on bare scalars" concern), but it needs real additions, not just reuse.

**b. Triangle-vs-plane intersection.** Confirmed nothing in `src/math/` does this — no file mentions "Plane" or "Triangle" (grepped `src/**` for `Plane|Quaternion|RotateVector|TransformPoint|Triangle`; only `RigidTransformPivot_MATH.h`/`.cpp`, `Placement_Transform_PROC.h`, and three unrelated UI files matched, none of which do plane/triangle classification). This is genuinely new.

**c. Point-in-polygon / grid rasterization.** Read both candidates in full — neither is reusable:
- `HeightOcclusion_MATH.h` is alpha-blend weighting math for the `MaterialProportions` DATA field (thickness×contrast clamped to a window, capped by remaining visibility) — a 1D scalar-blend concern, not geometry.
- `JumpFloodDistanceField_MATH.h` is a seeded nearest-obstacle distance transform via jump flooding — grid-shaped, but solves "distance to nearest seed cell," not "is this point inside this polygon" or "fill this polygon's cells." Superficially adjacent only in that both touch a 2D grid.

Nothing in `src/math/` covers point-in-polygon or polygon rasterization.

## 2. Recommended new primitives

All sized/named per `ARCH_01_03_MathNaming.md` (`<Domain>_MATH`, optimized variant as a function suffix) and `ARCH_01_05_FileSizeCeilings.md` (soft 100 / hard 150 lines, functions ≤40 lines, one primary type per file).

**Extend `src/math/RigidTransformPivot_MATH.h`** (currently 43 lines — room to grow within the soft ceiling) with:
- `RotateVectorByQuaternion(qx,qy,qz,qw, vx,vy,vz, outX,outY,outZ)` — the missing core 3D primitive everything else builds on (pure quaternion sandwich product, no transcendentals).
- `TransformPointByRigidTransform(px,py,pz, posX,Y,Z, qx,qy,qz,qw, scaleX,Y,Z, outX,Y,Z)` — scale → rotate → translate, matching `Placement_Transform_PROC.h`'s own instance-transform order.
- `InverseTransformPointByRigidTransform(...)` — subtract translation, rotate by the conjugate quaternion (negate x,y,z — trivial for a unit quaternion), then **multiply by the precomputed reciprocal of scale** (reuse `Reciprocal_MATH::Reciprocal`, per Constitution §3's reciprocal-multiply pillar — never divide per point).
- `InverseTransformPlaneByRigidTransform(normalX,Y,Z, pointOnPlaneX,Y,Z, posX,Y,Z, qx,qy,qz,qw, scaleX,Y,Z, outNormalX,Y,Z, outD)` — the actual primitive this feature needs: transforms one plane (normal + a point on it, or normal + world distance) into an instance's local space via the inverse above. **Correctness nuance to flag explicitly for the ingestion/PROC designs, not resolved here:** under *uniform* scale, rotating the normal by the inverse quaternion is exact. Under *non-uniform* per-axis scale (the struct shape already supports it, per `Placement_Transform_PROC.h`'s `scaleX/Y/Z`), a normal must transform by the inverse-transpose of the linear part — i.e. rotate by the inverse quaternion, then divide each axis by that axis's scale (reciprocal-multiply again) rather than multiply, followed by a renormalize. I have not confirmed whether `.sanmodel`-driven placed props ever carry genuinely non-uniform scale in practice (SanGen's own `SampleInstanceTransform` samples a single uniform `scale` today) — **the ingestion expert should confirm this**, since it decides whether the cheap uniform-scale path is always legal or the primitive must always take the general inverse-transpose path.

**New file `src/math/TrianglePlaneIntersection_MATH.h`** — genuinely missing, ~50-70 lines, two functions to stay under the 40-line function ceiling:
- `ClassifyTriangleAgainstPlane(normal, d, v0,v1,v2) → per-vertex signed distances + a sign bitmask` (pure dot-product-minus-d, no transcendentals).
- `TrianglePlaneIntersectionSegment(...)` — given the classification, lerp the 0/1/2 crossing edges to produce the intersection segment endpoints (`t = distA/(distA-distB)`, then FMA-lerp the two vertices).
Accuracy class: **Exact** — pure algebra (subtract/multiply/compare/lerp), no transcendentals, so it is decision-exact and trivially bit-identical if ever ported to GPU — no accuracy-class tension at all.

**Possible (contingent, not designed here) — `src/math/PointInPolygon_MATH.h`.** If the rasterization design needs a standalone even-odd/winding point-in-polygon test as a building block (rather than a specialized scanline fill it owns entirely itself), that's a small, separately-namable Exact-class primitive. I'm flagging the shape, not designing the rasterizer — that decision belongs to the Generator Expert's PROC design, informed by `NAVMAP_MODIFIER_BLOCKER_SPEC.md` §7's existing (currently ad hoc, outside-SanGen) mask-to-rectangle Python workflow, which is the closest prior art.

## 3. Performance / dispatch assessment

Read `ARCH_04_DispatchContract.md`, `DISPATCH_INTERFACE_SPEC.md`, and `OPTIMIZATION_PILLARS.md` directly. This workload does not map onto any of the four existing dispatch-policy rows (Noise/Blend/Mask/Thermal, Erosion/Flow, Placement, Bake) — it is a new stage that needed its own `DispatchPolicy` row; that assignment was out of my authority to make, but **`ARCH_22_14_GeometryMathAndDispatch.md` §22.14 point 3 has since ratified the row below as the binding `DispatchPolicy` for this stage — CPU-only, no GPU dispatch — this is no longer an open recommendation awaiting a decision:**

**CPU is comfortably sufficient; GPU is not warranted.** Reasoning:
- This runs at map-authoring/export time (one-shot batch over placed instances), not a per-frame or resident-grid pass — the class of workload `OPTIMIZATION_PILLARS` pillar 15 (GPU-resident compute) targets is iterative resident-grid work (Noise/Blend/Erosion) that amortizes upload/dispatch/readback cost across many passes. Here, mesh vertex buffers vary per unique `.sanmodel` asset and the job is a single classification pass per instance — upload/readback/shader-setup overhead would likely dominate for any realistic per-map instance count, unlike the resident stages.
- Per-instance work is embarrassingly parallel (each instance's triangle classification touches only its own mesh + its own once-transformed local plane, no shared mutable state) — `OPTIMIZATION_PILLARS` pillar 12 (lock-free chunked multithreading, partition by instance) is the correct first lever, not GPU dispatch.
- Within an instance, per-vertex signed-distance classification (`dot(N,V) - d`) vectorizes trivially across `FloatVector_MATH`'s 8-wide lanes once vertex positions are laid out SoA — a legitimate, benchmark-backed follow-up work-order once real prop-mesh triangle/instance counts from actual maps are known, not a load-bearing decision now.

**The per-instance plane-transform (not per-vertex world-transform) is the load-bearing performance principle here, worth stating explicitly, not just implicitly through the primitive's existence.** Transforming one plane into local space is O(1) per instance regardless of mesh size; forward-transforming every vertex to world space is O(vertex count) per instance. For the "massively scaled prop" case flagged — a huge mesh where only a sliver of vertices sit near the water plane — this is not a minor optimization: it is the difference between O(instances) and O(instances × vertices), and it also **replaces a full ~15-FLOP rigid-transform per vertex with a single ~4-FLOP dot-product-minus-compare per vertex** once the plane is local. This is exactly Constitution §3's loop-invariant-hoisting spirit (hoist the one cheap-to-transform quantity — the plane — out of the expensive-to-touch loop — the vertices), and it is the concrete reason `InverseTransformPlaneByRigidTransform` should exist as a tested, reused MATH primitive rather than inline math in the PROC/IO code: it makes the "transform the plane, never the mesh" discipline structurally hard to regress.

## 4. Determinism — confirmed, does not need bit-identical cross-machine determinism

Read `DETERMINISM_SPEC.md` and `ARCH_04_DispatchContract.md` §4.5–4.6 directly. `DETERMINISM_SPEC`'s whole premise is a peer **regenerating** gameplay-authoritative output locally from shared settings+seed, so it must match bit-for-bit without transferring the file. This feature does not fit that shape: per `NAVMAP_MODIFIER_BLOCKER_SPEC.md` §7 (the existing, proven-live precedent), the rectangle list is baked once, at SanGen export time, into the map's own Lua data — a static artifact every player loads, exactly like `heightmap.raw` is loaded when a map is distributed as a full package rather than regenerated from seed. Mesh content (`.sanmodel` geometry) is fixed asset data, not seed-derived, so intersecting it against a fixed water-level plane is not part of the seed→map regeneration surface `DETERMINISM_SPEC`'s Exact chain governs at all — even under SanGen's own optional Deterministic settings+seed sharing mode, nothing re-runs this computation per peer machine.

**Practical effect:** no requirement for portable minimax transcendentals, no requirement for ordered-reduction/fixed-point discipline, and standard `std::sqrt`/hardware FMA in the new MATH primitives above are legal on pure performance grounds — there is no determinism tax to design around here.

**One confirmation I could not settle myself and am flagging rather than assuming past:** this conclusion depends on the other two experts' designs placing the blocker computation as a one-shot export/IO-time action on the authoring machine — not as a stage a peer's own Deterministic-mode pipeline re-runs. If either design instead threads this through the seed-driven PLACEMENT/PIPELINE re-run path, the conclusion flips and `DETERMINISM_SPEC`'s gate would apply. Worth a one-line confirmation in each of their designs.
