# STEP200 — VIEW popup layout fix: fixed-width rows, no collapsing, left visibility toggle, expanded blend-mode list

**Layer:** UI. **Domain:** `src/ui/Application_ViewLayersPopup_UI.cpp`/`.h`, `Application_Draw_UI.cpp`,
`DraggableListWidget_UI.h` (additive change only, no default-behavior change),
`PreviewComposite_Settings_UI.h`, `PreviewComposite_Color_UI.h` (CPU), `PreviewComposite_Color_UI.glsl`
(GPU), `PreviewComposite_GpuProgram_UI.cpp` (GPU `#define` generation) — the blend-mode enum is
consumed on both the CPU and GPU compositing paths, so all four must move together.

> **Depends on STEP150.** STEP150 has an in-flight, uncommitted change to `DraggableListWidget_UI.h`
> (`DrawRowAffordances`, adding an optional per-row custom button between lock and delete). Do not
> begin editing `DraggableListWidget_UI.h` for this ticket until STEP150 is confirmed committed —

## Root problem
The human reported the VIEW toolbar popup (map preview layer list) has a broken layout and is
missing blend-mode options, compared against the pre-rebuild "v1" implementation
(`gui/widgets/Widget_MapCanvas.cpp:24-95`, a legacy tree still git-tracked in this repo, not a
branch). Confirmed by direct code reading:

1. **Popup keeps growing wider until it stops.** `Application_ViewLayersPopup_UI.cpp:55-56` draws
   `ImGui::Combo("Blend Mode", ...)` and line 87 draws `ImGui::SliderFloat("Opacity", ...)`, neither
   preceded by `ImGui::SetNextItemWidth(...)`. Both sit inside `ImGui::BeginPopup` (an auto-fit-to-
   content window) via `Application_Draw_UI.cpp:52-56`. An unconstrained-width item inside an
   auto-resizing popup is a known ImGui feedback pattern (width → content region avail → item width →
   width...) matching the reported symptom exactly. v1's equivalent (`Widget_MapCanvas.cpp:69`) uses
   `ImGui::SetNextItemWidth(100)` before its combo — the fix v1 already had.
2. **Every row is collapsible when it shouldn't be.** `DraggableListWidget_UI.h:86-96` forces every
   row through `ImGui::CollapsingHeader(...)`, giving each layer a disclosure arrow and expand/collapse
   behavior. v1 (`Widget_MapCanvas.cpp:44-51`) draws each row as a single-line `ImGui::Selectable`,
   nothing collapses. This widget is shared by other `DraggableList` consumers across
   `src/ui/*Tab_UI.cpp`, so the fix must be additive/opt-in, not a default-behavior change.
3. **Drag handle is the whole row, not the name.** `DetectRowDragAndDrop()`
   (`DraggableListWidget_UI.h:122-138`) currently uses the full header/row as the drag source. v1
   (`Widget_MapCanvas.cpp:44-51`) uses the name `Selectable` itself as the drag source/target — the
   human wants the name to be the click/drag target, matching v1.
4. **Blend-mode combo has a label; the human wants none.** `Application_ViewLayersPopup_UI.cpp:54`
   draws `ImGui::Combo("Blend Mode", ...)` with a visible label. v1 (`Widget_MapCanvas.cpp:68-70`)
   uses a label-less `ImGui::Combo("##blend", ...)`.
5. **Blend-mode list is missing most of v1's options.** Current enum,
   `PreviewComposite_Settings_UI.h:26`: `enum class PreviewBlendMode { Replace, AlphaBlend, Add,
   Multiply, Maximum, Minimum };` (6 modes), mirrored in
   `Application_ViewLayersPopup_UI.cpp:22-24`. v1's list (`Widget_MapCanvas.cpp`, its own
   `blendModeNames[]`): `{"None","Normal","Add","Subtract","Multiply","Divide","Overlay","Screen",
   "Soft Light","Hard Light"}` (10 modes). The human wants at least every v1 mode present, while
   keeping the newer modes already in v2 (Replace, Alpha, Max, Min).
   - `PreviewBlendMode` drives real compositing math on two paths, both switching over the same enum:
     CPU in `PreviewComposite_Color_UI.h:50-58`, GPU in `PreviewComposite_Color_UI.glsl:23-27,35` via
     `PREVIEW_BLEND_*` `#define`s generated by `PreviewComposite_GpuProgram_UI.cpp:43-48`. Adding new
     enumerators requires extending all three, numerically matching between CPU and GPU.
   - `PreviewComposite_Settings_UI.h:6-8`'s header comment confirms these settings do **not**
     serialize into `mapGeneratorData` (preview-only, not part of the save format), so the enum is
     safe to extend by appending new values — no migration/versioning concern.
   - v1 `Normal` is the same operation as v2's existing `AlphaBlend` — do not add it as a duplicate
     enumerator, just note the naming difference is cosmetic.
   - v1 `None` is superseded by requirement 6 below (a dedicated visibility toggle) — do not port it
     as a blend enumerator.
   - **Final list to implement** (append-only, order matters for existing indices — do not reorder
     the first 6): `Replace, AlphaBlend, Add, Multiply, Maximum, Minimum` (unchanged, existing) +
     `Subtract, Divide, Overlay, Screen, SoftLight, HardLight` (new, ported from v1). Update both the
     enum and the `previewBlendModeNames[]` display-string table together.
6. **No visibility toggle left of the name.** `DraggableListWidget_UI.h:106-118`
   (`DrawRowAffordances`) draws visibility/lock/delete right-aligned via
   `kAffordanceStripWidthPixels = 76` (line 36); there is no left-of-name toggle. v1 had no equivalent
   widget either (its "visibility" was implied by `Blend != None`) — this is a **new addition**, not a
   restoration. `ApplyViewLayerSignal<T>()` (`Application_ViewLayersPopup_UI.h:22-33`) already applies
   `ToggleVisibility` signals correctly (keep using this signal, no new signal kind needed).
   Confirmed the human's constraint is already satisfied by existing code:
   `PreviewComposite_Prepare_UI.cpp:48-50` has `if (!layer.bEnabled) continue;` inside
   `BuildLayerConfigurations`, which only ever consumes already-baked `mapFields` — toggling
   visibility skips the compositing record only, never the underlying bake/calculation. So this point
   is pure UI layout (move the existing toggle to the left of the name), not new plumbing.

## Fix approach
1. **Fixed-width items.** Add `ImGui::SetNextItemWidth(...)` (match v1's `100`px, adjust if the
   popup's fixed row width dictates otherwise — see point 2) before the blend `Combo` and the opacity
   `SliderFloat` in `Application_ViewLayersPopup_UI.cpp`. As defense-in-depth, add
   `ImGui::SetNextWindowSizeConstraints(...)` with a fixed max width before the `BeginPopup` call in
   `Application_Draw_UI.cpp` so no future unconstrained item can reintroduce runaway growth.
2. **Flat, non-collapsible rows — additive widget change.** Add an opt-in row-layout parameter to
   `DraggableList<T>` (e.g. `DraggableListRowLayout { Collapsible (default, unchanged), Flat }`,
   read the real current template/param shape first). Default stays `Collapsible` so every other
   `DraggableList` consumer (Props, Decals, Markers, other tabs) is unaffected. In `Flat` mode: no
   `CollapsingHeader`, no indent; draw left-to-right: visibility toggle → `SameLine` → name as
   `ImGui::Selectable` (this becomes the actual drag source/target, satisfying point 3) → `SameLine`
   → the row body inline on the same line (blend combo / opacity slider) → right-aligned lock/delete
   strip via `DrawRowAffordances`, now called with a new param to suppress its own visibility icon
   (since it's already drawn on the left) — read `DrawRowAffordances`'s post-STEP150 signature fresh
   and add this param consistently with however STEP150 shaped its own optional-button param.
3. **Name as drag handle.** Point `DetectRowDragAndDrop()`'s drag source/target at the name
   `Selectable` added in point 2, not the whole row, when in `Flat` mode. `Collapsible` mode keeps its
   current whole-row drag behavior unchanged.
4. **Remove the blend-mode label.** Change `Combo("Blend Mode", ...)` to `Combo("##blend", ...)` in
   `Application_ViewLayersPopup_UI.cpp:54-59`.
5. **Expand the blend-mode enum.** Add `Subtract, Divide, Overlay, Screen, SoftLight, HardLight` to
   `PreviewBlendMode` (`PreviewComposite_Settings_UI.h:26`), appended after `Minimum` — do not
   reorder existing values. Mirror the additions in `previewBlendModeNames[]`
   (`Application_ViewLayersPopup_UI.cpp:22-24`). Implement the new cases in the CPU switch
   (`PreviewComposite_Color_UI.h:50-58`) and the GLSL switch (`PreviewComposite_Color_UI.glsl:23-27,35`),
   and extend the GPU `#define` generator (`PreviewComposite_GpuProgram_UI.cpp:43-48`) to match —
   verify CPU and GPU enumerator values line up numerically.
6. **Left-of-name visibility toggle.** Covered by point 2's row layout — reuse the existing
   `[o]/[-]##visibility` affordance widget and its existing `ToggleVisibility` signal, just move its
   draw position to the leftmost slot in `Flat` mode. No change to `ApplyViewLayerSignal` needed.
7. Wire `DrawTerrainSection()`/`DrawOverlaySection()` (`Application_ViewLayersPopup_UI.cpp:35-62,74-90`)
   to construct their `DraggableList` with `DraggableListRowLayout::Flat`.

## Explicit out-of-scope
- The "preview layers per marker TYPE (Alloy, Units, Props, Reclaim, Spawns, etc.) on the VIEW
  button" feature raised separately — conceptually adjacent but a distinct feature request, not a
  layout fix; tracked separately pending a decision with the human.
- Any change to `Params::HeightBlendMode` (the unrelated geometry height-blend enum, labels in
  `LayersTab_UI.cpp`) — a different feature, do not conflate with `PreviewBlendMode`.
- Any change to what `DrawRowAffordances`'s optional custom button (added by STEP150) does — this
  ticket only adds a param to suppress the built-in visibility icon when the caller draws its own.
- Making `Collapsible` mode's drag-and-drop or affordance layout match `Flat` mode — existing
  `DraggableList` consumers outside this popup are unaffected by design.
- `ARCH_14_07_ViewToolbar.md:10`'s mention of terrain rows using the shared `Combo_UI` widget: the
  actual `Combo_UI.cpp:15-24` unconditionally draws a label and sizes to full content-region width,
  which conflicts with points 1 and 4 above. This ticket uses a raw `ImGui::Combo` with
  `SetNextItemWidth` instead of `Combo_UI` for this popup's blend selector; reconciling the ARCH text
  is out-of-scope here and should be flagged to the ARCH Expert separately.
