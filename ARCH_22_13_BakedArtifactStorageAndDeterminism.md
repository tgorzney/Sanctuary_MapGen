### 22.13 Baked blocker-rectangle storage, the Exact/Deterministic-chain question, and the new one-shot PIPELINE bake responsibility

Rules on the question both the Format Expert's §5 and the Generator Expert's §4.2 independently
reasoned toward but explicitly declined to assert as law, flagging it for ARCH by name.

**1. Storage RULED: an ordinary `Params::` field, never a companion export-only `.lua` artifact**
(Format doc Q4 → option (a); Generator doc Q2 → option (a), bake unconditionally). This is the
load-bearing structural choice, not merely a hedge. It mirrors `ARCH_18_02_IngestedDataDeterminism.md`'s
already-shipped footprint-bake mechanism exactly — no third mechanism is invented. And because
`Params::` is definitionally the "settings" `DETERMINISM_SPEC.md`'s "the host sends only
settings+seed" already transports, a `Params::`-resident rectangle list travels bit-identically to
every shared-generation peer automatically, as ordinary recipe payload — not because it is
independently recomputed and happens to agree, but because it is literally the same transported
bytes, exactly like any other already-baked `Params::` scalar. This closes the Format doc's Q4/flag
6 without opening a new IO Architecture Expert shared-generation transfer-contract exception; the
companion-`.lua` alternative, which would need exactly that exception, is rejected.

**2. The Exact/Deterministic-chain question RULED: this feature sits entirely outside Constitution
§4's Deterministic sub-mode / `DETERMINISM_SPEC.md`'s bit-exact cross-machine regeneration bar —
settled, not merely "arguably outside."** Three independent lines of reasoning across the four
documents (Format §5, Generator §4.2, Compute Optimization §4) converge on the same answer, and
point 3 below makes it structural rather than conditional: the mesh-intersection computation **never
runs inside the live PROC regeneration DAG** (`RegisterStages()`), because the new PIPELINE
responsibility below categorically bars it from ever being part of what any peer machine
"regenerates from settings+seed." What each peer receives is the already-computed `Params::`
-resident rectangle list (point 1), transported, never recomputed. `DETERMINISM_SPEC.md`'s bit-exact
bar governs values independently regenerated by more than one machine; this value is never
independently regenerated by more than one machine (only the author's), so the bar does not apply —
**not because the value is exempt or decorative** (it plainly is not — a navmesh blocker is directly
pathing-authoritative, arguably more so than "collidable props," `DETERMINISM_SPEC.md`'s own listed
example), but because its correctness mechanism is **transport**, not recomputation.

**3. New PIPELINE responsibility class, named: the one-shot, human-triggered bake entry point**
(resolves the Generator doc's Q6). Distinct from both existing PIPELINE responsibilities:
- **Not §3.3's dirty-hash DAG orchestration** — never registered via `AddStage`/`RegisterStages()`,
  never auto-re-run, no dirty-hash edges.
- **Not §16.3's stateless query passthrough** — §16.3 point 1 requires the wrapped function be
  "already, independently pure... no DATA dependency, no side effects... re-callable every frame
  with no state carried between calls." This bake reads `Data::PlacementResults.props` plus
  IO-sourced mesh data and **writes** a new `Params::` value — it fails both the "no DATA
  dependency" and "no side effects" tests by design, so §16.3's mechanism cannot be stretched to
  cover it.

**Binding shape:**
- Lives in its own narrow `PIPELINE` file (e.g. `NavmeshBlockerBake_PIPELINE.h/.cpp`), sized/scoped
  like `PreviewDriver_PIPELINE.h` — the same "narrow single-purpose PIPELINE file" precedent §16.3
  point 2 already names.
- Runs strictly after Placement — the same dependency `BuildSpatialGridSet`/`BuildRuleBucketIndex`
  already have (real precedent for "derived work that must see Placement's final output").
- **Never** wired into `RegisterStages()` — invoked only by an explicit human action (a UI trigger
  or an export step), never by Generate, never by any dirty-hash recompute.
- Snapshots the current `Data::PlacementResults.props` + `Params::Water` + the current
  mesh-ingestion IO table; runs the §22.12 PROC kernels; writes the resolved rectangle-list
  `Params::` field (`ARCH_22_15_NavmeshTabParamsShape.md`). A later Placement re-run does **not**
  auto-invalidate the bake — mirrors ARCH §18.2 point 4's "un-baked/stale is not an error state"
  verbatim. A staleness hint (fingerprint compare) is a legitimate UI affordance; auto-recompute is
  not.
- This generalizes ARCH §18.2 point 1's "PIPELINE/UI writes a `Params::` value as a human-triggered
  action" shape, previously exercised only by footprint's simple scalar lookup-and-copy — here it
  genuinely must invoke real PROC kernels, which `UI` cannot legally reach directly (§3.1); `PIPELINE`
  is the only legal doorway.

**4. `DETERMINISM_SPEC.md` amended** — a short clarifying paragraph added directly below its
`## Scope` section (not a scope-list addition, since the value is neither independently regenerated
nor visual/exempt): some gameplay-authoritative-adjacent `Params::` fields (baked footprint per §18.2;
navmesh blocker rectangles per this ruling) achieve cross-machine parity by **transport**, never by
independent per-machine recomputation, and sit outside this spec's regeneration bar by construction —
they must never be wired into a live-regenerated PROC stage, which would reopen exactly the hazard
this spec's bar exists to catch.
